# Architecture rules
- Trading-card shops call `purchase_csb_tcg_card` with only a catalog ID; fixed server prices, locked payment and collection writes share one transaction, and clients have read-only collection access to prevent free cards.
- Bookmark and saved-link icons use the existing token artwork in a multi-resolution favicon, Apple touch icon and web manifest; keep these references versioned together so browsers can refresh cached icons.
- Currency swaps use the authenticated `swap_game_currency` RPC with fixed server-owned rates and transactional locking; never accept client amounts or separate debit/credit requests, because failures must not lose funds.
- Balance caps are interim safeguards, not proof of valid game rewards; do not close economy security findings until payouts are validated from server-owned game state.
- Badge shops call `purchase_csb_badge` with only a catalog ID; only that atomic server operation may grant a badge, while clients may update only `active`, so purchases and cosmetic identity cannot be forged.
- Rune upgrades use `purchase_csb_upgrade` to derive current level, cost and energy capacity under locks; direct upgrade writes are revoked to prevent free levels and partial purchases.
- Wheel color unlocks use `spin_color_wheel` to spend one Key and choose a uniform server-owned prize atomically; clients may only equip colors and animate the returned outcome, preventing forged unlocks.- Keys are earned only through server functions (`award_holder_keys`, `claim_daily_reward`, swaps, wheel); browsers may only lower Key balances, because client-reported Key gains were forgeable.
- Missions use `csb_mission_step` (server spends energy, advances progress) and `csb_claim_mission` (fixed reward × streak); client mission writes are revoked.
- Lucky Chain uses `lucky_chain_action` for locked entry, server randomness, version-checked progression and one-time payouts; clients never supply outcomes or reward amounts, and active runs resume without another entry charge.
